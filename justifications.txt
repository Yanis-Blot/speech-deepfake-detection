1. **Comparability with the literature.** The official ASVspoof2019 LA split (train/dev/eval) is the one used by every published baseline (LFCC-GMM, CQCC-GMM, RawNet2, AASIST…). Changing it would make our results incomparable to the field's reference numbers, while the brief explicitly asks us to motivate our choices "using state-of-the-art."

2. **Preserving the dataset's scientific purpose.** The split isn't arbitrary: train/dev only contain known attacks (A01–A06), eval exclusively contains unseen attacks (A07–A19). This exact partition is what lets us measure generalization to never-seen synthesis techniques — the core problem the brief poses. Changing it would void that measurement.

3. **Protocol integrity verified empirically, not assumed.** We checked it ourselves (not just trusted the documentation): 0 speakers shared between train/validation/test, 0 duplicate files, no attack leakage between splits. The official split is therefore reliable as-is.

4. **The volume (25k in train) is not a real compute constraint on our infrastructure.** With feature caching (computed once, not recomputed every epoch), a full training run on the official train set takes anywhere from a few minutes (CNN) to 1–2h (full wav2vec2 fine-tuning) on the school's GPU server — well within reach. The perceived slowness initially came from repeatedly recomputing spectrograms every epoch, not from the data volume itself.

5. **Merging train+validation would have gained volume at an unjustified methodological cost**: losing a dev set that's independent in the strict protocol sense, for a gain that addresses no real constraint (neither compute nor performance) once feature caching is in place. The cost/benefit doesn't justify deviating from the official protocol.

6. **Final decision, documented**: official split kept intact (train=25,380, validation=24,844, eval=71,237 — never touched during training); speed gained through descriptor caching, not through shrinking the dataset.

7.## **Decision — Local Dataset Storage vs. Hugging Face Streaming** : 1\. **Training stability.** Local storage eliminates dependency on network connectivity and provides more consistent training performance across multiple epochs. 2\. **Dataset already downloaded.** The complete ASVspoof2019 LA dataset (121,461 recordings) is already stored in our Docker container, making streaming unnecessary. 3\. **Efficient training and reproducibility.** Local storage supports random access, full shuffling, and feature caching, facilitating repeated experiments and fair comparisons between models. 4\. **No GPU memory disadvantage.** PyTorch DataLoaders process audio in mini-batches without loading the entire dataset into GPU memory. 5\. **Final decision:** Keep the original dataset locally in Docker, apply preprocessing separately, and use mini-batch loading with optional feature caching.

8. **Project Infrastructure and Version Control.** The project is developed in a remote Docker container on the school's GPU server, with a shared GitHub repository for version control and collaboration. At the end of each working day, changes are committed and pushed to GitHub to maintain an up-to-date version of the project and track its development history.

11 . presentatio nppt : expliquer :
_ Un **audio numérique** est une représentation d'un son sous forme d'une suite de valeurs numériques appelées **échantillons**.

Chaque échantillon représente la **valeur de l'amplitude du signal sonore à un instant précis**.

Ces échantillons sont obtenus grâce à un processus appelé **échantillonnage**, qui consiste à mesurer le signal sonore à intervalles de temps réguliers.

Le nombre d'échantillons prélevés par seconde est appelé **fréquence d'échantillonnage**, exprimée en hertz (Hz).

Par exemple, une fréquence d'échantillonnage de **16 kHz** signifie que le signal est mesuré **16 000 fois par seconde**.

et expliquer aussi :

Parce que le son dans la réalité est un signal continu, alors qu'un ordinateur travaille avec des données numériques.

L'échantillonnage permet donc de transformer ce signal continu en une suite de mesures prises à des instants précis.


12 . Nous avons ajouté la fonction `leading_silence_duration()` afin de mesurer la durée du silence précédant la parole dans chaque enregistrement. 15. Pourquoi des zéros et pas une répétition de l’audio ?

Deux raisons techniques, qui rejoignent ce qu’on vient de voir avec le biais de silence :

La répétition crée un signal artificiel qui n’existe pas dans la réalité. Si on boucle un extrait de 2s pour atteindre 4s, le point de raccordement (fin → début) crée une discontinuité brutale (un “clic”) qui n’a rien à voir avec de la parole. Un modèle basé sur un spectrogramme pourrait très bien détecter ce clic comme un artefact haute fréquence — et si, par malchance, les fichiers courts sont plus souvent bonafide ou plus souvent spoof dans le dataset, le modèle apprendrait encore un raccourci inventé par le prétraitement, exactement comme le biais de silence qu’on vient de tester.
Avec le padding par zéros + le mask, on peut dire explicitement au modèle “ceci n’est pas du vrai contenu, ignore-le”. Avec la répétition, on ne peut pas faire ça : le signal répété ressemble à du vrai signal, donc le mask ne pourrait plus distinguer “réel” de “artificiel” — toute la logique de masquage qu’on a mise en place (et qui doit arriver dans le CNN plus tard) s’effondre.

19. Pourquoi une représentation 2D (spectrogramme + CNN2D)

On a fait du 2D pour transformer le waveform brut en une représentation temps-fréquence (un spectrogramme), afin que le modèle puisse exploiter des motifs localisés à la fois dans le temps et dans la fréquence — exactement comme une image. Cette approche permet de réutiliser directement les architectures convolutives 2D vues en cours (CNN, Unet), offre une représentation interprétable visuellement (on peut afficher et comparer des spectrogrammes bonafide vs spoof), et bénéficie du partage de poids et de l'invariance locale des convolutions, qui corrige le problème observé avec notre MLP sur waveform brut (surapprentissage massif, EER train=0.059 vs validation=0.432, faute d'une structure exploitable par une simple couche dense).

Pourquoi le STFT (et pas Mel, MFCC, ou un traitement 1D)

On a choisi le STFT (en échelle linéaire, pas Mel) car les artefacts caractéristiques des techniques de synthèse vocale (vocoders, GANs) se concentrent typiquement dans les hautes fréquences — une zone que l'échelle Mel compresse volontairement pour imiter la perception auditive humaine, au détriment de l'information la plus discriminante pour la détection de spoofing. Le STFT linéaire préserve une résolution fréquentielle uniforme sur tout le spectre, ce qui est cohérent avec les pratiques documentées en anti-spoofing (préférence pour des échelles linéaires/CQT plutôt que Mel/MFCC, utilisées plutôt en reconnaissance vocale classique).

prq pas MFCC = Mel (perd déjà les hautes fréquences) + DCT (perd en plus les détails fins du spectre) → c'est une double perte d'information, chacune retirant un type de signal potentiellement discriminant pour détecter un deepfake

Justification du choix "spectrogramme STFT, directement donné au CNN" (sans DCT, sans réduction en coefficients)
Source 1 — comparaison directe entre types de spectrogrammes

Une étude récente sur ASVspoof 2019, "Deepfake Audio Detection Using Spectrogram-based Feature and Ensemble of Deep Learning Models" (Pham et al., 2024), compare explicitement plusieurs transformations — le signal audio brut est transformé en différents spectrogrammes via trois méthodes : Short-time Fourier Transform (STFT), Constant-Q Transform (CQT) — et entraîne des modèles CNN/RNN directement sur ces spectrogrammes. Résultat : les spectrogrammes STFT ont généralement donné les meilleures performances, avec un ensemble final atteignant un EER de 0.03 sur ASVspoof 2019.
Lien : https://arxiv.org/html/2407.01777v1 
fraunhofer
arxiv

Source 2 — justification du choix "spectrogramme brut" plutôt que "coefficients cepstraux" (DCT)

Un papier de synthèse sur la détection de deepfake vocal confirme explicitement ce choix architectural : les features de type "image" comme le Mel-spectrogramme ou le CQT-spectrogramme sont généralement traitées comme des images et passées à des classifieurs CNN, et surtout : le spectrogramme nécessite moins de puissance de calcul que l'extraction de coefficients spectraux via DCT, tout en garantissant une bonne précision de détection.
Lien : https://arxiv.org/pdf/2404.13914 (A Survey on Speech Deepfake Detection)
